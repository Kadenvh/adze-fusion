# W1-5 — Cross-platform reality: Mac vs Windows for Fusion connectors and add-ins

**Date:** 2026-06-11
**Researcher:** workflow sub-agent (Stage 1 Wave 1)

## Summary (3-5 sentences)

Autodesk documents near-total feature parity between Fusion on Mac and Windows, with two explicit caveats: "some Add-in may be only compatible with certain OS" and slower machining simulation on Mac. Fusion has been ARM64-native on Apple Silicon since July 2023 (universal binary, Rosetta 2 still a listed dependency for "some specific commands"), and the embedded Python — upgraded to 3.14 in the January 2026 update — runs in-process, so pure-Python add-ins are cross-platform while anything with compiled native extensions must match both OS and CPU architecture. The official Autodesk Fusion MCP Server is built into Fusion itself (Preferences > General > API, port 27182), not an App Store add-in; the App Store listing "MCP Server for Autodesk® Fusion®" the prior pass attributed to Autodesk is actually third-party (AuraFriday MCP-Link), and that listing 404'd on direct fetch today. Linux has no official story beyond the browser client; Autodesk states Fusion cannot be installed on Linux.

## First principles (what the thing IS, stripped of marketing)

Fusion is one codebase shipped as a per-user (no-admin) install on two desktop OSes: a Win64 build (Windows 11 23H2+ only) and a macOS universal binary (x86_64 + arm64) living under `~/Library/Application Support/Autodesk/webdeploy/production/{40-char hash}/`. Add-ins execute inside Fusion's process: Python add-ins run on the interpreter Fusion embeds (currently 3.14), inheriting Fusion's CPU architecture; C++ add-ins are platform-and-architecture-specific binaries (.dll vs .dylib, x86_64 vs arm64). "Cross-platform Fusion add-in" therefore means: pure-Python source + no native-extension wheels + no OS-specific paths. The official MCP server is a feature flag inside Fusion, not a distributable artifact.

## Findings

### 1. Official system requirements, Mac vs Windows, 2026

From Autodesk's system requirements page, fetched 2026-06-11 ([System requirements for Autodesk Fusion](https://www.autodesk.com/support/technical/article/caas/sfdcarticles/sfdcarticles/System-requirements-for-Autodesk-Fusion-360.html)):

- **Windows:** "Windows 11, 23H2 (Build 22631 or newer)" only — Windows 10 is gone. Min 8 GB RAM (rec 32 GB+), DirectX 11 GPU. Windows-on-ARM: "ARM64 devices can run Fusion on Windows 11 using XtaJIT64/Prism emulation. This functionality has not yet completed certification by Autodesk Fusion."
- **macOS:** minimum "macOS 14 Sonoma" ("OpenCore Legacy Patcher is not supported"); recommended "macOS 15.7 Sequoia or newer / macOS 26 Tahoe or newer". Min 4 GB RAM (rec 16 GB+), Intel i5 or Apple M1 minimum. Dependencies include "Rosetta 2 — Note: While Autodesk Fusion itself is a native Apple silicon application, some specific commands are transitioning to ARM64 and will prompt for installation of Rosetta 2 as-needed." A rendering caveat is flagged: "Relief Pattern appearance on macOS 14 w/ Apple silicon."
- A browser client exists for any "HTML-5 compatible web browser."

Feature parity is documented directly: "Fusion on Mac and Windows offer the same features. However, some Add-in may be only compatible with certain OS. Also, using Fusion for manufacturing, the machining simulation may be slower on Mac." — [Is there a difference between Fusion on Mac and Windows](https://www.autodesk.com/support/technical/article/caas/sfdcarticles/sfdcarticles/Is-there-a-difference-between-Fusion-on-Mac-and-Windows.html), Autodesk Support, dated Nov 18, 2025, fetched 2026-06-11.

### 2. Is the add-in API surface identical on macOS?

Autodesk documents a single API: "Fusion has a single API that can be used from Python, C++, or TypeScript" ([Python Specific Issues](https://help.autodesk.com/cloudhelp/ENU/Fusion-360-API/files/PythonSpecific_UM.htm), fetched 2026-06-11). No Windows-only API area is documented anywhere I could find; the parity article's "some Add-in may be only compatible with certain OS" refers to compiled add-in binaries, not API surface. Real platform differences sit one layer down:

- **Palette/HTML UI engine:** Fusion "is switching from CEF to the Qt Web Browser"; the `useNewWebBrowser` flag selects the engine, and `adsk.fusionSendData` is synchronous under CEF but asynchronous (Promise-based) under Qt ([Using Palettes and Browser Command Inputs](https://help.autodesk.com/cloudhelp/ENU/Fusion-360-API/files/Palettes_UM.htm), fetched 2026-06-11). Historically the engines diverged by OS — "the browser engine Fusion uses is Chrome on Windows OS and Safari on Mac" ([Fusion 360 API: Work with Custom Palette — Manufacturing DevBlog, 2017](https://adndevblog.typepad.com/manufacturing/2017/09/fusion-360-api-work-with-custom-palette.html), via search) — so legacy palette behavior differences by OS are real; the Qt transition converges them.
- **Mac-specific load failures exist** at the binary level: Autodesk has a KB for a startup error "Could load the addin in /Users/(...)/Library/Application Support(...)/NaMachineBuilder10.dylib" on macOS Ventura ([KB article](https://www.autodesk.com/support/technical/article/caas/sfdcarticles/sfdcarticles/Could-load-the-addin-in-Users-Library-Application-Support-NaMachineBuilder10-dylib-pops-up-while-initiating-Fusion-on-MacOS-Ventura-13-5-1.html), via search, fetched 2026-06-11).

A systematic catalog of Mac-specific API bugs: **could not determine** — no official known-issues list by platform was found in my carve.

### 3. Apple Silicon: ARM-native Fusion and add-ins

- Fusion runs ARM64-native since the July 2023 update: "If you're running Fusion 360 on a M1 or M2 chip, Fusion 360 will automatically run the native ARM64 version"; "The main Fusion 360 application and its default add-ins now all run natively on Apple silicon. However, some individual processes and back-end services still temporarily require Rosetta 2" ([Running Fusion 360 on Apple Silicon Machines FAQ](https://www.autodesk.com/products/fusion-360/blog/running-fusion-360-on-apple-silicon-faq/), fetched 2026-06-11). The 2026 system-requirements page still lists Rosetta 2 as a dependency (see Q1).
- Fusion "is installed as a universal binary — it contains code for both x86_64 and ARM64," with an "Open using Rosetta" Get-Info toggle that "enables a universal app to use plug-ins, extensions, or other add-ons that do need Rosetta, because they haven't yet been updated to support Apple silicon" ([Running Intel add-ins on Apple silicon Fusion using Rosetta 2](https://www.autodesk.com/support/technical/article/caas/sfdcarticles/sfdcarticles/Running-Intel-add-ins-on-Apple-silicon-Fusion-360-using-Rosetta-2.html), fetched 2026-06-11). The FAQ's answer to "Will my installed Fusion 360 add-ins be compatible with Apple silicon?" was "Initially, no. You'll need to enable the 'Open using Rosetta'" (same FAQ, fetched 2026-06-11) — i.e., Intel-compiled add-ins force whole-app Rosetta mode.
- Python add-ins run on Fusion's embedded interpreter in-process, so they execute arm64-native when Fusion is native [inference from the above; no explicit Autodesk statement found]. The corollary is verified in the wild: the embedded interpreter was upgraded to **Python 3.14 in the January 2026 update** (from 3.12), and packages shipping compiled native extensions broke — "Fusion updated to an embedded Python 3.14 interpreter, and that breaks many packages that ship compiled native extensions, especially ones that now include Rust-based binaries (which cryptography does)" ([Fusion 360 Python 3.14 update breaks cryptography/Google auth imports — Autodesk Community, Feb 2026](https://forums.autodesk.com/t5/fusion-api-and-scripts-forum/fusion-360-python-3-14-update-breaks-cryptography-google-auth/td-p/14020343), fetched 2026-06-11). The prior pass's "Python 3.7" claim is **stale by two upgrade cycles** (3.7 → 3.9.7 in 2022 per [OpenBOM blog](https://www.openbom.com/blog/autodesk-fusion-360-python-changes-and-openbom-add-in), fetched 2026-06-11 → 3.12 → 3.14).

### 4. Official Autodesk Fusion MCP add-in on Mac

Correction to the prior pass: the official Fusion MCP is **not an App Store add-in at all**. Per official docs it is "exposed by Fusion when running locally," enabled by checking "the Fusion MCP Server (runs locally on this device) checkbox" under **Preferences > General > API**, default port 27182, "Local-only," and "Desktop-only. Does not work with the Fusion web client" ([Autodesk Fusion MCP Server help](https://help.autodesk.com/view/ADSKMCP/ENU/?guid=ADSKMCP_FusionDesktopMcp_autodesk_fusion_mcp_server_html) and [Connecting to the Autodesk Fusion MCP Server](https://help.autodesk.com/view/ADSKMCP/ENU/?guid=ADSKMCP_FusionDesktopMcp_connecting_to_the_fusion_mcp_server_html), both fetched 2026-06-11). No OS restriction is documented; the Claude Desktop setup flow (Settings > Extensions > Fusion) is OS-neutral. Explicit official "works on macOS" wording was not found — absence of restriction, not positive confirmation [unverified for end-to-end Mac].

The App Store listing `id=7269770001970905100` ("MCP Server for Autodesk® Fusion®", Mac variant) is **third-party**: search snippets identify it as AuraFriday's MCP-Link product (support `ask@aurafriday.com`, docs at [AuraFriday/Fusion-360-MCP-Server](https://github.com/AuraFriday/Fusion-360-MCP-Server), claiming "Windows 10/11 or macOS 10.15 or later") (via search, fetched 2026-06-11). Its forum "announcement" thread is by community user OceanHydroAU (2025-11-04), not Autodesk ([forum thread](https://forums.autodesk.com/t5/fusion-api-and-scripts-forum/driving-fusion-via-ai-using-mcp-server-add-in-announcement/td-p/13881165), fetched 2026-06-11). Direct fetches of the listing (both `os=Mac` and `os=Win32_64`) returned **404** on 2026-06-11 while search indexes still show it — current live status [unverified]. A marketplace search for "MCP" today returns 11 matches, mostly Revit connectors, all visibly "Win 64" ([marketplace search](https://apps.autodesk.com/FUSION/en/List/Search?isAppSearch=True&searchboxstore=FUSION&facet=&collection=&sort=&query=MCP), fetched 2026-06-11).

### 5. Install path, signing, and permissions on macOS

Official paths ([How to install an add-in or script in Autodesk Fusion](https://www.autodesk.com/support/technical/article/caas/sfdcarticles/sfdcarticles/How-to-install-an-ADD-IN-and-Script-in-Fusion-360.html), Autodesk Support, dated Apr 10, 2026, fetched 2026-06-11):

- Windows: `%appdata%\Autodesk\Autodesk Fusion\API\AddIns` (Scripts: `...\API\Scripts`); hidden-folder note.
- macOS: `~/Library/Application Support/Autodesk/Autodesk Fusion/API/AddIns`; "Hidden folders must be enabled in the Library folder."
- Note: community repos (e.g., ndoo's bridge) still document `.../Autodesk Fusion 360/API/AddIns` — the docs' "Autodesk Fusion" vs the long-standing on-disk "Autodesk Fusion 360" folder name is unresolved [unverified which exists on current builds].

Signing/Gatekeeper: Fusion itself installs per-user under `~/Library/Application Support/Autodesk/webdeploy/production/{hash}/` (Rosetta KB above) — no admin rights, and Autodesk has a KB for Gatekeeper blocking the installer ("The identity of the developer cannot be confirmed…" — [KB](https://www.autodesk.com/support/technical/article/caas/sfdcarticles/sfdcarticles/Problem-install-Fusion360-on-macOS.html), fetched 2026-06-11). Pure-Python add-ins copied as source are loaded by Fusion's embedded interpreter and are not Gatekeeper-notarized apps; quarantine xattrs on downloaded archives affect executables/dylibs (standard macOS mechanics — general knowledge, not Fusion-specific documentation). No Autodesk doc requiring signing/notarization of Fusion add-ins was found; App Store-distributed installers (.pkg/.app) carry the publisher's signing burden.

### 6. Mac-specific issues community developers report

Evidence in my carve is thinner than expected, but concrete items: (a) Intel-built add-ins failing on Apple Silicon until the Rosetta toggle or a universal rebuild (Rosetta KB + FAQ above); (b) the macOS Ventura dylib load-error KB (Q2); (c) hidden `~/Library` tripping manual installs (Autodesk's own install doc flags it); (d) legacy palette engine divergence (Chrome/Win vs Safari/Mac, Q2) causing HTML-UI behavior differences; (e) machining simulation slower on Mac (official parity article); (f) vendor add-in Mac errors, e.g. SnapMagic's Fusion plugin error Q&A ([snapeda.com](https://www.snapeda.com/questions/question/fusion-360-mac-plugin-error/), via search). Targeted searches for r/Fusion360 Mac add-in threads returned little indexable content — community Mac pain is mostly visible through Autodesk's own KBs [empirical: search-coverage observation].

### 7. Linux

No native support: "Autodesk Fusion cannot be directly installed on Linux. It is only available on Windows and Mac operating systems" ([Can Autodesk Fusion be installed on Linux?](https://www.autodesk.com/support/technical/article/caas/sfdcarticles/sfdcarticles/Is-there-any-way-to-install-Fusion-360-in-Linux.html), Autodesk Support, dated April 2026, via search — direct fetch failed, fetched 2026-06-11). The browser client is the only sanctioned path on Linux hardware (system-requirements page lists browser access). Community workaround exists ([cryinkfly/Autodesk-Fusion-360-for-Linux](https://github.com/cryinkfly/Autodesk-Fusion-360-for-Linux), Wine-based, unsupported). Critically for adze: the official Fusion MCP Server is "Desktop-only. Does not work with the Fusion web client" — so there is **no Linux story for Fusion AI integration at all**, not even via browser.

## Decision implications for adze-fusion

- **Pure-Python or pay twice.** The cross-platform guarantee holds only for source-distributed Python with no native-extension wheels. Any compiled dependency multiplies the support matrix: Win-x64, Mac-x86_64, Mac-arm64 — and the Jan 2026 Python 3.14 jump shows Autodesk will break native deps without ceremony. Vendor dependencies as pure-Python or talk to a sidecar process.
- **Treat the embedded interpreter as volatile.** Three Python upgrades (3.7→3.9.7→3.12→3.14) each broke add-ins. Design for interpreter churn (no .pyc shipping, minimal stdlib-plus assumptions).
- **Mac parity is real and cheap for the add-in layer; budget for HTML-UI testing.** If adze uses palettes, target the Qt browser (`useNewWebBrowser=True`, async fusionSendData) to avoid legacy per-OS engine divergence.
- **Don't claim "official MCP requires our installer."** The official server is a built-in checkbox; adze's value must sit elsewhere. Note App Store AI listings skew Windows-only ("Win 64") — shipping a genuinely Mac-tested add-in is a visible differentiator.
- **Drop Linux from scope** with a clear ADR note: no native client, and the web client is excluded from MCP.
